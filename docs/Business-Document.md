## 1. System Overview

**ZCRM** ("Zalo Sales CRM") is a self-hosted CRM purpose-built for sales teams that work over **Zalo**, Vietnam's dominant consumer messaging platform. Instead of asking sales teams to adopt a new tool, ZCRM connects directly to their existing Zalo accounts (via the unofficial `zca-js` client) and layers CRM structure — contacts, tags, deal stages, appointments, lead scoring, reporting — on top of conversations that already happen in Zalo.

Current release line: **v3.4.x** (`CHANGELOG.md`); `v1.x`–`v3.3.x` are inherited upstream history from `locphamnguyen/ZaloCRM`, which this project relicensed to AGPL-3.0 and continued developing.

**Key features** (verified against the codebase, not just marketing copy):
- Multi-account ("multi-nick") Zalo management with QR login, auto-reconnect, and per-nick daily send caps to avoid platform blocks.
- Real-time chat (Socket.IO) with attachments (image/video/file), reactions, stickers, bank/QR card rendering, message templates.
- A two-tier contact model (**Contact** = person, **Friend** = per-nick care record) — see §3.
- Lead Scoring engine: 4-axis score (Engagement/Intent/Fit/Velocity), auto-decay, auto-tagging, stuck-lead detection.
- Appointments with automated reminders and a public token-authenticated action link (no login required for the sales rep acting on a Zalo-shared link).
- A new reporting suite (Overview / Nick Fleet / Sales / Pipeline / Engagement / Audit) added 2026-06-17, alongside a legacy basic-reports view kept for backward compatibility.
- Bidirectional **Zalo ↔ Telegram bridge** with media re-upload and duplicate-suppression.
- Per-organization AI assistant (Anthropic / Gemini / OpenAI-compatible, covering Qwen and Kimi) for reply drafting, sentiment, and summaries.
- Public REST API (`X-Api-Key`) with a full 19-endpoint-group reference (`docs/zalocrm-api/`) and a Postman collection, intended for the ZCRM mobile app and third-party integrations.
- Grant-based RBAC with department/team scoping, audit logging, and OTP-gated privacy mode for "main nick" content.
- PWA scaffolding present (`vite-plugin-pwa` dependency, manifest) but **currently disabled** — registration is commented out in `frontend/src/main.ts` pending a Vite 8 compatibility fix. Mobile support itself (distinct from installable-PWA) *is* live: a dedicated mobile layout, bottom nav, and offline-tolerant mutation queue.

**Target users:** see §4 (Actors & Permissions) — no separate persona work exists beyond what's inferable from the RBAC/reporting feature set.

**Success metrics:** not tracked in this repository — see §9 Open Questions.

- **Backend**: Fastify 5 + Prisma 7 + PostgreSQL 16, Node 20 ESM. Entry point `backend/src/app.ts` — boots plugins (CORS, JWT, security headers, per-user rate limiting, multipart), Socket.IO with pre-route auth, ~45 route registrations, then ~15 background jobs (cron + one BullMQ worker), then reconnects any Zalo accounts with saved sessions. **25 business modules** under `backend/src/modules/` — up from the 23 recorded in the 2026-06-16 architecture doc; `automation` and `lead-pool` moved into the Enterprise (`_ee`) bundle, and `config`, `devices`, `lists`, `push` were added as new Community modules.
- **Frontend**: Vue 3 + Vuetify 4 + Pinia + Vite, `@`-aliased single shared `api` axios instance plus two justified per-domain wrappers (`media.ts`, `public-branding.ts`). **51 views** — up from the 25 recorded in the same 2026-06-16 doc, driven mainly by the Settings redesign (12 files) and a new Reports shell (7 files).
- **Data layer**: PostgreSQL 16 holds **108 Prisma models** (up from 93 as of 2026-06-16), Redis 7 backs BullMQ and the per-nick rate-limit counters, and object storage (MinIO by default, or S3/Cloudflare R2 via a `STORAGE_DRIVER` switch) holds chat attachments and media library assets.
- **Realtime**: Socket.IO, JWT-verified at handshake (fixed a prior cross-tenant WS IDOR by deriving room membership server-side from the verified token rather than trusting client-supplied org/user IDs).
- **Zalo integration**: `ZaloAccountPool` (`backend/src/modules/zalo/zalo-pool.ts`) — an in-memory map of live per-account SDK sessions with epoch-tagged reconnect handling to prevent stale-listener flapping, wrapped in per-account/per-category rate limiting (Redis-backed, fail-open) that reads its limits from an org-overridable `SdkLimit` table rather than hardcoded constants.
- **Open-core seam**: `backend/src/shared/ee-registry/` (automation, event-bus, integrations hook tables with no-op defaults) and `frontend/src/_ee` vs `_ee-stubs` (Vite alias, resolved by directory existence, no env flag). Neither `_ee` directory exists in this checkout — this is a pure Community-edition build.

## 3. Domain Model

The schema (`backend/prisma/schema.prisma`, 4,050 lines) has **108 models** and deliberately only **2 enums** — the project convention favors `String` columns with an allowed-values comment over Prisma enums (documented in `backend/prisma/CLAUDE.md`).

**Core entities:**
- **`Organization`** — the tenant root; nearly every other model cascades from it. Also stores a surprising amount of per-org operational config directly on the model itself (reminder offsets, welcome-message templates, sweep intervals) rather than a dedicated settings table.
- **`User`** — `role` (owner/admin/member) is kept only for a documented "dual-read window"; real authorization is via `permissionGroupId`. Email is optional (Vietnamese sales staff often log in by phone only).
- **`ZaloAccount`** — one row per connected Zalo "nick." Carries session data, `privacyMode` (main nicks get content blurred for non-owners), `disconnectReason` (manual vs. passive — controls auto-reconnect eligibility), and per-nick daily send caps.

**The "two-book" model** (`Contact` vs. `Friend`) is the project's foundational domain decision:
- **`Contact`** = the "cha" (parent) record — the person-level view managers and dashboards see. Visible parents are `contacts WHERE merged_into IS NULL`. It carries fields explicitly *aggregated* from its `Friend` rows: `leadScore` (a `MAX()` over Friend scores), nick counters (`acceptedNicksCount`/`pendingNicksCount`/`chattingNicksCount`), and a computed `priorityScore` (`leadScore×0.55 + engagementScore×0.30 + trendBoost`, per an in-code comment).
- **`Friend`** = the "con" (child) record — one row per `(zaloAccountId, zaloUidInNick)` pair, the actual sale/nick-level care card. This is where the *real* 4-axis lead score lives, along with `friendshipStatus`, `relationshipKind` (with a documented legacy-junk value, `none`, that the frontend coerces to `chatting_stranger`), and per-pair message previews — deliberately isolated per nick so a sale sharing visibility with a teammate can't see another nick's private preview.
- Relationship: **1 Contact → N Friend**. A separate `ContactAccess` junction layers primary/collaborator sharing on top, and a `parentContactId` soft-link (distinct from hard `mergedInto` merge) groups the same human across different Zalo identities.

**Other major domain clusters** present in the schema: Conversation/Message (ordered by Zalo's own BigInt Snowflake `zaloMsgIdNum`, not `sentAt`, because some self-listen events lack a timestamp), Telegram bridge state, Lead Scoring config (`ScoringConfig`, `ScoreSignalRule`, `StageTransitionRule`, `StuckThreshold`, `NbaTemplate`), RBAC (`Department`, `DepartmentMember`, `PermissionGroup`), Media Library, and — notably — **Automation/Marketing tables** (`Block`, `AutomationSequence`, `AutomationCampaign`, `TriggerQueueEntry`, `CareSession`, ...), **Lead Pool** tables, and **Facebook Lead Ads / Zalo OA** tables that exist in the schema even though the *code* that operates on them lives in the absent `_ee` bundle — the schema is shared across editions, the application logic is not.

## 4. Actors & Permissions

- **Owner** — first user created at org setup; full access, bypasses grant checks.
- **Admin** — near-owner privileges via the same role-bypass fallback in `requireGrant`.
- **Member** — governed entirely by grant-based RBAC: an 18-resource × 5-action (`access/create/edit/delete/view_all`) permission matrix resolved from `User.permissionGroupId → PermissionGroup.grants` (JSON), modeled explicitly on a competitor CRM's permission screen per an in-code comment.
- **Department leader/deputy** — a scoping layer on top of the grant matrix (`owner-scope.ts`) that determines whether a user's dashboard/report view spans their whole department tree (`canViewAll`) or just themselves.
- **Legacy role-string path** (`requireRole`) still functions but is explicitly not to be used for new routes (`backend/CLAUDE.md`).
- **Public API consumers** — external systems authenticated via `X-Api-Key`, resolved to an `orgId` through a separate `apiKeyAuth` preHandler, deliberately kept out of the JWT/session chain.
- **Privacy-gated viewers** — even authorized users can be blocked from seeing "main nick" content unless they've unlocked a per-session OTP-based privacy gate (`privacy.ts` Pinia store); a global response-scanning "leak guard" runs on every response as a second line of defense (warn-only, not auto-redacting).

## 5. Business Workflows

**Connecting a Zalo account:** user initiates QR login → `ZaloAccountPool.loginQR()` establishes a zca-js session → account and listener are registered in the in-memory pool → session persisted so a server restart can auto-reconnect. Manual disconnects set `disconnectReason='manual'`, which excludes the account from all subsequent auto-reconnect sweeps ("ngắt là ngắt thật" — the code's own phrasing for "disconnect means disconnect").

**Inbound/outbound messaging:** zca-js listener fires → message handler resolves/creates `Conversation`/`Contact`/`Friend` rows → Socket.IO emits a scoped patch to `org:<orgId>` room → frontend `use-chat.ts` applies the patch to reactive state. A 5-minute polling backup (`zalo-message-sync.ts`) exists as a safety net behind the primary event-driven path.

**Lead scoring:** signal events (inbound/outbound message, meeting) feed a 4-axis score on `Friend`; an hourly (jittered) decay job and daily stuck-detection/auto-tag jobs run via `scoring-scheduler.ts`; `Contact.leadScore` is recomputed as the `MAX` across a person's Friend rows.

**Appointments:** created against a Contact, reminded via two cron sweeps (next-day notice + 5-minute overdue-flip), and can be marked done/cancelled from a **public, token-authenticated link** shared over Zalo — deliberately not requiring the acting sale rep to be logged in on that device.

**Zalo group scanning:** enqueued as a BullMQ job (`enqueueGroupScan`) → processed with concurrency 1 (explicitly to avoid Zalo's anti-spam heuristics firing on parallel scans) → resumable, chunked in batches of 50 members, retried up to 3 times with exponential backoff. See `docs/Queue-Flow-Diagrams.md` for the full flow.

**Zalo ↔ Telegram bridge:** subscribes to an internal `bridgeBus` `'message.persisted'` event fired after a message commits → mirrors to a per-conversation Telegram forum topic → media is fetched from object storage and re-uploaded as bytes (Telegram cannot fetch internal storage URLs directly) → echo-loop suppression via a `sentVia==='bridge'` marker.

## 6. API & Integrations

- **Internal API** (`/api/v1`, JWT-authenticated) — consumed by the SPA and, per the mobile-app feature line in `CHANGELOG.md` v3.4.0, the ZCRM Mobile App.
- **Public API** (`X-Api-Key`) — 19 documented endpoint groups (`docs/zalocrm-api/api-documentation.md` + Vietnamese translation + PDF + Postman collection), covering contacts, messaging, appointments, Zalo-account proxy config, and outgoing webhooks (`message.received`, `message.sent`, `contact.created`, `zalo.connected`, `zalo.disconnected`).
- **Outgoing webhooks**: org-admin-configured URL, HMAC-SHA256-signed if a secret is set, 10-second timeout, and SSRF-guarded (rejects loopback/RFC1918/link-local/cloud-metadata IPs before dispatch — a documented fix for a real historical vulnerability, see §8).
- **AI providers**: Anthropic, Gemini, and an OpenAI-compatible client that also covers Qwen and Kimi — configured per-organization, API keys encrypted at rest, masked in the UI.
- **Storage**: MinIO (default, Docker Compose-bundled) or S3-compatible endpoints including Cloudflare R2, switched via `STORAGE_DRIVER` with a content-hash dedup key shared across both drivers.
- **Telegram bridge**: optional (enabled by setting `TELEGRAM_BRIDGE_BOT_TOKEN`), separate from the generic "Telegram bot notify" integration provider.
- **Other integration providers**: Google Sheets sync, Zapier webhook (also SSRF-guarded).

## 7. Configuration & Deployment

- **Docker Compose** (`docker-compose.yml`): `app`, `db` (Postgres 16), `redis` (AOF-persisted, hard dependency of BullMQ — not optional), `minio` (S3 API port intentionally public so Zalo's CDN can fetch attachment URLs; admin console bound to loopback only), `minio-init` (bucket bootstrap, anonymous *download* only, never upload), `backup` (daily pg_dump, 7-day/4-week/3-month retention), `clamav` (optional AV scanning, fail-open by default, no port exposed to host).
- **Required secrets** (fail-fast in production if missing/short/default, `backend/src/config/index.ts`): `JWT_SECRET`, `ENCRYPTION_KEY` (≥32 chars each), `DB_PASSWORD`, `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` (Compose itself hard-fails on these — no more `minioadmin/minioadmin` default, a documented historical fix).
- **Background jobs**: one BullMQ queue (`group-scan`, Redis-backed) plus roughly 14 `node-cron`/interval-based jobs covering Zalo health checks, friend sync, session refresh, appointment reminders, lead-scoring decay, engagement classification, and media trash GC. Full inventory in `docs/Queue-Flow-Diagrams.md`.
- **Deploy orchestration**: `scripts/zalocrm-deploy.sh` (used by both `scripts/install.sh` and the documented manual path) — handles both fresh install and upgrade, including automatic DB backup before migration.
- **No CI/CD**: `.github/workflows/` does not exist; tests run locally only.

## 8. Testing Strategy

- **Backend**: 83 `*.test.ts` files (`backend/tests/`), matching the count documented in `backend/CLAUDE.md` exactly. Only one test is module-colocated (`zalo-profile-capture.test.ts`) — the stated "colocated or `tests/`" convention resolves almost entirely to the centralized location in practice. A 10-file `tests/security/` suite directly exercises auth/refresh-rotation, tenant-guard, socket-auth, and security-header middleware. Notable regression tests exist for two real historical vulnerabilities: `custom-report-sqli.test.ts` (the v3.3.1 SQL injection fix) and `ssrf-guard.test.ts` (the webhook SSRF fix).
- **Frontend**: exactly 2 spec files, an intentionally thin baseline per `frontend/CLAUDE.md`. The established pattern — extract pure, framework-free decision logic into a co-located `*-logic.ts` file (e.g. `use-work-scope.ts` / `work-scope-logic.ts` / `work-scope-logic.spec.ts`) and unit-test only that file under Node — is the template for any future frontend test coverage; Vuetify component mount-testing is explicitly avoided.

## 9. Appendix

### Glossary
- **Nick** — a single connected Zalo account within the pool; one org can run many nicks.
- **Two-book model** — the Contact (person/manager view) vs. Friend (per-nick care record) domain split; see §3.
- **Ghost nick** — a `ZaloAccount` stuck in a transient state (e.g. `qr_pending`) with no live session, cleaned up by an hourly cron.
- **Main nick** — a Zalo account flagged `privacyMode='main'`, whose content is blurred from non-owner viewers unless privacy is unlocked via OTP.
- **EE / CE** — Enterprise Edition (commercial `_ee` bundle, absent from this checkout) vs. Community Edition (this codebase).
- **Tenant context** — the `AsyncLocalStorage`-carried `{orgId, userId, role}` that scopes every org-scoped Prisma query.

### Open Questions
- **EE bundle internals are unknowable from this checkout** — the `automation`, `lead-pool`, and Facebook/Zalo-OA integration *logic* live in the absent `_ee` bundle; only their hook interfaces and shared schema are visible here. Anything said about EE behavior beyond the hook contracts is inference, not verified fact.
- **`backend/src/modules/campaign/campaign-routes.ts` appears orphaned** — defined but never registered in `app.ts` (confirmed via grep); worth confirming with the team whether this is dead code, mid-migration to EE, or a registration bug.
- **Three separate AES-256-GCM implementations exist**; only one (`integrations/_shared/token-encryption.util.ts`, keyed by `TOKEN_ENCRYPTION_KEY`) is actually used for the live encrypted column (`AppSetting.valueEncrypted`). `shared/crypto/aes-gcm.ts` (keyed by `FB_TOKEN_ENC_KEY`) has zero importers in this checkout — presumably consumed by the absent `_ee/facebook` bundle. `config.encryptionKey` (env `ENCRYPTION_KEY`) is defined with the same fail-fast treatment as `JWT_SECRET` but is never referenced again anywhere in `src/` — worth confirming whether it's vestigial or reserved for a future column.
- **The "Friend Invite Queue"** referenced by `docker-compose.yml`'s `FRIEND_INVITE_TEST_MODE` env var has no implementation in Community core — only a `Contact.friendInviteSentCount` counter column exists here; the actual queue/worker is presumably in the absent `_ee/automation` bundle.
- Concrete business metrics/KPIs (active orgs, retention, conversion) are not present in this repo — likely tracked externally.
- Pricing/tiering of the commercial Enterprise license is not visible in code — only the mechanism (license key env var + `_ee` bundle presence) is.
