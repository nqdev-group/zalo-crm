## 1. Executive Summary

ZCRM is a self-hosted, open-core CRM for sales teams operating over Zalo, Vietnam's dominant consumer messaging app. It is currently at release **v3.4.0** (2026-06-20), a major version that added a UI/dashboard redesign, security hardening (refresh-token rotation, CSP, audit log), a new reporting suite, a Zalo↔Telegram bridge, and a full mobile-app API surface. The codebase shows continuous, active investment — 108 domain models, 25 backend modules, 51 frontend views, 83 backend tests — well past MVP maturity. It is dual-licensed (AGPL-3.0 Community + commercial Enterprise), with an EE feature set (automation engine, lead pool, Facebook/Zalo-OA lead import) delivered as a separate closed bundle that plugs into open hook points in this codebase.

## 2. Problem Statement

Vietnamese SMB sales teams already run customer conversations through personal or business Zalo accounts, because that's where their customers are — not because it's a good sales tool. Generic CRMs require customers to move to a new channel (email, a web form, a different chat app), which sales teams and customers both resist. Without CRM structure layered onto Zalo itself, teams lose: a shared view of who's talking to which customer across multiple Zalo "nicks," pipeline/stage tracking, appointment follow-through, and any way to measure lead quality or rep performance — all invisible to a manager who can't see what happens inside someone's personal Zalo app.

## 3. Solution Overview

ZCRM connects directly to a team's existing Zalo accounts via the `zca-js` client library, then layers standard CRM primitives on top: contacts, pipeline stages, tags, appointments, lead scoring, and reporting — without requiring the customer-facing channel to change. It runs self-hosted (Docker Compose), so an operator's customer data and conversation history stay on infrastructure they control. The core differentiator is the **two-book domain model** (Contact = person, Friend = per-nick care record), which lets a manager see one merged customer view while individual sales reps retain per-nick working context — solving the "who owns this conversation" problem that arises once more than one person on a team touches the same customer across multiple Zalo nicks.

## 4. Target Audience

- **Primary**: Vietnamese SMB sales/customer-service teams already prospecting and closing over Zalo.
- **Secondary**: Sales managers/admins who need cross-nick, cross-rep visibility — served by RBAC department scoping, audit logs, and the "Vận hành Nick Zalo" (Zalo-account-operations) report.
- **Tertiary**: Self-hosting technical operators (the deployment audience) — Docker Compose literate, comfortable running `scripts/zalocrm-deploy.sh` against a VPS.
- No formal user personas exist in the repo; the above is inferred from feature design (RBAC, department scoping, Vietnamese-first UI copy) and documentation language.

## 9. User Stories & Acceptance Criteria

*(Reconstructed from code behavior — these describe what the system does, not authored backlog items.)*

- **As a sales rep**, I want to see all conversations across every Zalo nick I have access to filtered by a "work scope," so I don't lose track of which conversations are mine. *Acceptance*: `use-work-scope.ts`/`work-scope-logic.ts` persist scope to `localStorage`, validate it against server-granted `accessibleIds` on every load (never trust the client-cached scope alone), and reload the thread if an incoming message falls outside the current scope.
- **As a manager**, I want a merged view of a customer even if they've messaged multiple nicks, so I don't double-count or lose history. *Acceptance*: `Contact` is the canonical parent (`WHERE merged_into IS NULL`), aggregating `leadScore` as `MAX()` across all linked `Friend` rows.
- **As an org owner**, I want a refresh-token compromise (stolen token replayed) to revoke the entire session family, not just the leaked token. *Acceptance*: `refresh-token-service.ts` detects reuse of an already-rotated/revoked token and revokes the whole `familyId` chain, distinguishing genuine reuse from a benign same-tab race via a grace window.
- **As a sales rep**, I want to mark an appointment done from a Zalo-shared link without re-logging into the CRM on my phone. *Acceptance*: `/appointments/action` is an explicitly public, token-authenticated route (`meta.public = true`), bypassing the global auth redirect.
- **As an org admin**, I want group-scan jobs to run one at a time per account so Zalo doesn't flag the account for spam-like parallel access. *Acceptance*: the `group-scan` BullMQ worker runs at concurrency 1 by explicit design comment.

## 10. Technical Requirements

- **Language/runtime**: Node.js 20 (backend, ESM), TypeScript (both backend and frontend).
- **Frameworks**: Fastify 5 (backend), Vue 3 + Vuetify 4 + Pinia (frontend).
- **Persistence**: PostgreSQL 16 via Prisma 7 ORM; Redis 7 for BullMQ + rate-limit counters.
- **Object storage**: MinIO (bundled) or any S3-compatible endpoint (AWS S3, Cloudflare R2) via a driver switch.
- **Security**: 15-minute JWT access tokens + rotating refresh tokens with reuse detection; AES-256-GCM for encrypted-at-rest secrets; CSP + standard security headers; SSRF guard on all admin-configurable outbound URLs (webhooks); per-user rate limiting; fail-fast boot checks on production secrets.
- **Scalability targets**: not formally documented; the architecture (single-process Fastify app, in-memory `ZaloAccountPool`) implies a single-instance deployment model rather than horizontal scaling — worth flagging as a constraint if multi-instance deploy is ever considered (the shared BullMQ Redis connection helper's docstring hints at a Bull Board multi-worker future, but this is speculative).
- **Integration requirements**: `zca-js` (unofficial Zalo client, MIT-licensed, via the `openzca` bridge lineage), Telegram Bot API, Anthropic/Gemini/OpenAI-compatible AI APIs, generic webhook/Zapier/Google Sheets sync.

## 11. Constraints & Dependencies

- **Legal/ToS risk**: `zca-js` is an *unofficial* client; using it may violate Zalo's Terms of Service and risk account suspension — explicitly disclosed in `README.md`'s legal notice. This is a first-order business risk inherent to the product category, not a bug.
- **Single-VPS deployment model**: Docker Compose, no Kubernetes/multi-node story, no CI/CD pipeline (`.github/workflows/` doesn't exist).
- **In-memory session state**: `ZaloAccountPool` lives in one Node process's memory — a restart drops all live Zalo sessions (though saved credentials allow auto-reconnect at boot).
- **EE dependency for a chunk of the marketed feature set**: automation rules execution, lead-pool distribution, and Facebook/Zalo-OA lead import are schema-present but logic-absent in Community edition — a Community-only deployer cannot use these despite the tables existing.
- **Anti-block heuristics are hand-tuned, not guaranteed**: all the rate-limiting/staggering/concurrency-1 patterns are best-effort mitigations against Zalo's undocumented anti-spam detection, not a contractual SLA.

## 15. Risks & Mitigation Strategies

| Risk | Likelihood | Impact | Mitigation Present in Code |
|---|---|---|---|
| Zalo detects automation, suspends accounts | Medium (inherent to unofficial-client category) | High (core product depends on live Zalo sessions) | Per-nick daily caps, sequential/staggered sync, concurrency-1 group scan, configurable per-org `SdkLimit` overrides |
| Refresh-token theft | Low-medium | High (account takeover) | Rotation with reuse detection, whole-family revocation, audit logging |
| SSRF via admin-configured webhook URL | Low (requires a malicious/compromised org admin) | Medium | `ssrf-guard.ts` blocks loopback/RFC1918/link-local/metadata IPs (documented as hostname-literal only — DNS-rebinding TOCTOU is an acknowledged residual gap) |
| Cross-tenant data leakage | Low (defense-in-depth exists) | Critical (multi-tenant product) | `AsyncLocalStorage` tenant context + Prisma `$allOperations` guard + a documented, not-yet-default-enforced Postgres RLS layer (staged rollout, `config.rlsSetConfig` currently off by default) |
| Single-process Zalo session state loss on crash | Medium | Medium (temporary reconnect gap) | Persisted session data + boot-time reconnect sweep, hourly ghost-account cleanup |
| Orphaned/dead code accumulating (`campaign-routes.ts`, unused `encryptionKey` config, undeployed `zalo-label-mutate` queue) | Ongoing | Low-medium (maintainability) | None automated — flagged here as a housekeeping item, not a runtime risk |

## 16. Glossary

- **Nick** — a connected Zalo account within `ZaloAccountPool`.
- **Two-book model** — Contact (person) vs. Friend (per-nick care record); see Business-Document.md §3.
- **EE / CE** — Enterprise Edition (commercial, closed `_ee` bundle) vs. Community Edition (this AGPL-3.0 codebase).
- **Tenant context** — the `AsyncLocalStorage`-carried `{orgId, userId, role}` scoping every org-scoped query.
- **RLS** — Row-Level Security (Postgres feature); present as a staged, currently-optional enforcement layer beneath the application-level tenant guard.
- **Work scope** — a frontend-persisted set of Zalo account IDs defining which conversations a user is currently focused on.
- **Ghost nick** — a `ZaloAccount` stuck in a transient connection state with no live session.
