# Technical Specification: EE/CE Open-Core Seam

> Generated by `nqdev-codebase-analyst` (Phase 4) on 2026-08-21. Describes the shipped implementation as found in `backend/src/shared/ee-registry/`, `backend/src/app.ts`, and `frontend/vite.config.ts` / `frontend/src/_ee-stubs/`.

## 1. Overview

ZCRM is dual-licensed: an AGPL-3.0 Community edition (this codebase) and a commercial Enterprise edition delivered as a separate, closed `_ee` bundle. The seam between them is a deliberate architectural boundary — Community code must never import Enterprise code directly — implemented as directory-existence-gated module loading (backend) and Vite alias resolution (frontend), backed by no-op hook-table defaults so Community builds function correctly with zero EE code present.

## 2. Problem Statement

An open-core product needs Community code to (a) never hard-depend on proprietary code that isn't present in the open repository, and (b) still have well-defined extension points where the Enterprise bundle can inject richer behavior without forking or patching Community files. Without a disciplined seam, either the open repo accumulates dead imports that fail to build, or EE logic gets inline-branched into core code (`if (isEnterprise)`), which both projects' `CLAUDE.md` files explicitly forbid.

## 3. Proposed Solution

**Backend**: three hook-table registries (`automation.ts`, `event-bus.ts`, `integrations.ts` under `shared/ee-registry/`) expose typed function interfaces with safe no-op defaults. `app.ts` attempts `await import('./_ee/index.js')` via a runtime string (not a static literal, so TypeScript cannot statically resolve/typecheck it at compile time); if `_ee/` doesn't exist, the dynamic import throws, is swallowed, and a log line records "Community edition — _ee bundle absent." If present, the EE bundle calls `register*Hooks()` functions at boot to override the no-op defaults.

**Frontend**: `vite.config.ts` resolves the `@ee` import alias to `./src/_ee` if that directory exists on disk, else falls back to `./src/_ee-stubs` — computed once at config load, no environment variable involved. The stubs export empty arrays (`eeSettingsChildren`, `eeReportsChildren`, `eeTopRoutes`, `eeSettingsItems`, `eeTopNavShortcuts`) and `isExtension = false`, plus stub Vue components for automation-block and lead-pool UI slots that the EE bundle would otherwise fill.

## 4. Detailed Design

**Backend hook surface** (verified present, `_ee/` absent in this checkout):
- `AutomationHooks` (17 functions: `runAutomationRules`, `logEvent`, `onTagAdded`, `resolveBlockContent`, `renderTemplate`/`renderTemplateDetailed`, `emitLeadScoreThresholdIfCrossed`, `onFriendAccepted`, `sendStrangerFollowUp`, `onCustomerBlock`, `notifyCustomerBlock`, `onCustomerReaction`, `respawnNickWorkerIfActive`, ...). Defaults are all inert: e.g. `resolveBlockContent` returns `{ok: false, error: 'AUTOMATION_DISABLED'}`, `renderTemplate` is an identity function.
- `automationEventBus` — a thin `EventEmitter` wrapper that core modules (chat, contacts, zalo) `emit()` domain events into unconditionally; in Community, nothing subscribes, so it's a near-zero-cost no-op. Exposes an `onType(types, handler)` API mirroring what the extension engine's own bus would expose, so a subscriber module (e.g. `lists/list-event-handlers.ts`) works identically regardless of which edition is running.
- `integrations.ts` — narrowest registry, just `importFacebookLeads` (defaults to a `disabled` result) — isolating the generic sync engine from the Facebook-specific EE provider implementation.

**Three extension hook points in `app.ts`**: `registerExtensionEarly(app)` (before any core route registers), `registerExtensionRoutes(app)` (after all core routes), `startExtensionJobs(app, io)` (after core cron/worker startup) — giving the EE bundle well-defined places to add middleware, routes, and background jobs without needing to know Community's internal registration order.

**Frontend stub components**: beyond the empty-array stubs, `_ee-stubs/` also ships stub *component* files (`automation/chat-blocks/{AutomationBlocksPanel,BlockPickerPopup,BlockPreviewDialog}.vue`, `automation/components/{LeadNotifyConfigDrawer,LeadNotifyTimeline}.vue`, `lead-pool/components/LeadFloatingButton.vue`) — Community-edition UI code that references these slots renders an empty/no-op component rather than needing conditional rendering logic scattered through the real UI.

## 5. Technical Architecture

- `backend/src/shared/ee-registry/{automation,event-bus,integrations}.ts`
- `backend/src/app.ts` — `loadExtension()`, and the 3 extension hook call sites.
- `frontend/vite.config.ts` (lines 7–12) — `@ee` alias resolution.
- `frontend/src/_ee-stubs/` — `edition.ts`, `nav.ts`, `routes.ts`, plus stub components.

## 6. API Specifications

Not a public API — this is a build-time/boot-time composition mechanism, not a runtime-negotiated interface.

## 7. Database Schema

**Important, non-obvious finding**: the Prisma schema is **shared across editions** — EE-domain tables (`AutomationSequence`, `AutomationCampaign`, `TriggerQueueEntry`, `CareSession`, `LeadRequest`, `LeadPoolConfig`, `FacebookPageAccount`, `FacebookLeadgenForm`, `ZaloOaAppConfig`, ...) all exist in `schema.prisma` and thus in the Community database, even though no Community code operates on them. This means a Community deployment carries EE-shaped schema weight it never uses — a deliberate trade-off (one shared migration history) rather than a bug, but worth knowing when reasoning about schema size or planning a schema audit.

## 8. Security Considerations

The dynamic-string `import('./_ee/index.js')` pattern is specifically designed to prevent TypeScript from statically resolving the import at compile time (so Community can compile with zero knowledge of `_ee`'s existence) — this is a build-isolation technique, not a security boundary in the access-control sense; it doesn't prevent a Community deployment from having `_ee/` present (that's exactly the mechanism a licensed customer's build would use), it only prevents an *absent* `_ee/` from breaking the Community build.

## 9. Performance Requirements

Every core-module call into an EE hook (e.g. `automationEventBus.emit(...)`) executes even when EE is absent — these are designed to be cheap no-ops, but represent a small constant overhead on every relevant core code path (message send, tag add, friend accept, etc.) even in a pure Community deployment. Not measured/benchmarked in this codebase.

## 10. Testing Strategy

No test found that directly exercises `loadExtension()`'s absent-bundle fallback path (i.e., no test asserts "app boots cleanly with `_ee/` missing") — this is implicitly verified by the fact that the entire test suite runs successfully in this Community checkout where `_ee/` genuinely doesn't exist, but there's no dedicated regression test pinning that behavior. Worth flagging as a coverage gap given how load-bearing this boot path is.

## 11. Deployment & Operations

Presence or absence of `backend/src/_ee/` and `frontend/src/_ee/` on disk at build time is the entire edition switch — no environment variable, no feature flag, no license-key gate at the code level (a license key, per `.env.example`, presumably gates something within the EE bundle itself, but that's unverifiable from this checkout).

## 12. Timeline & Dependencies

Structural to the project since the AGPL-3.0 relicense (v3.4.0) formalized the open-core split; the underlying `automation`/`lead-pool` modules were moved out of Community core into this seam as part of that same release line (confirmed via `app.ts` comments referencing the migration).

## 13. Trade-offs & Rationale

- **Shared schema, split code** is simpler to maintain (one migration history) at the cost of Community carrying unused table definitions — reasonable for a small-to-medium schema, worth revisiting if the EE-only portion of the schema grows much larger relative to Community's.
- **No-op-default hook tables** over `if (isEnterprise)` branches is unambiguously the right call for open-core hygiene — it keeps Community code path-identical regardless of edition, and this codebase follows that discipline consistently (per the research pass, no EE inline-branch was found in core code).
- **Directory-existence as the sole edition switch** is simple and hard to misconfigure (no flag to forget to set), but means the *build* — not a runtime config value — determines edition; an operator can't toggle EE features without rebuilding with the `_ee/` bundle present.
