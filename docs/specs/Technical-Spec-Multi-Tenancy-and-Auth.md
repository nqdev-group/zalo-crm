# Technical Specification: Multi-Tenancy & Authentication

> Generated by `nqdev-codebase-analyst` (Phase 4) on 2026-08-21. Describes the shipped implementation as found in `backend/src/shared/tenant/`, `backend/src/modules/auth/`, and `backend/src/shared/database/prisma-client.ts`.

## 1. Overview

Every request in ZCRM operates within an organization ("org") boundary. Two independent mechanisms enforce this: (a) a request-scoped **tenant context** that every org-scoped Prisma query is checked against, and (b) a **JWT + rotating refresh token** authentication layer that establishes who the user is and which org they belong to before tenant context is ever entered. Together they are the load-bearing security boundary for a multi-tenant SaaS-shaped product.

## 2. Problem Statement

A single Fastify process serves many organizations. A single missed `orgId` filter in one query is a cross-tenant data leak — one customer's contacts, messages, or appointments becoming visible to another org. Manually adding `WHERE orgId = ...` to every query is error-prone at 108-model scale; the system needs a mechanism that fails loud (or at minimum, loud in logs) when a query against an org-scoped model runs without a resolved tenant.

## 3. Proposed Solution

`AsyncLocalStorage` (`tenant-context.ts`) carries `{orgId, userId, role, bypassTenantGuard, rlsConfigApplied}` through the async call chain of a request without threading it as an explicit parameter. A Prisma `$allOperations` extension (`tenant-guard.ts`) checks every write/read against a hardcoded 62-model allow-list (`org-scoped-models.ts`) and warns or throws if no context is present. This is layered *underneath* JWT authentication, which is the actual mechanism that resolves `orgId` in the first place.

## 4. Detailed Design

**Auth flow**: `POST /auth/login` accepts an identifier (auto-detected as email or Vietnamese phone, normalized to `84xxx`) + password, bcrypt-compares (cost 12), returns a `JwtPayload {id, email, role, orgId, tv}` as a 15-minute access token plus an opaque refresh token. `auth-middleware.ts` runs on every authenticated route: verifies the JWT, and — for legacy (non-`typ:'access'`) tokens only — does a DB `jwtTokenVersion` re-check per request; newer 15-minute tokens skip that DB roundtrip (accepting a worst-case 15-minute revocation SLA, with actual revocation enforced at the `/auth/refresh` boundary instead). It then calls `enterTenantContext({orgId, userId, role})`, which is what makes tenant-scoped queries legal for the rest of that request's async chain.

**Tenant flow**: `withTenant(orgId, fn)` is the explicit-scope equivalent for code that runs outside an HTTP request (cron jobs, the BullMQ group-scan worker, socket handlers). `runSystemQuery(fn)` sets `orgId: '*'` and `bypassTenantGuard: true` — the sole sanctioned escape hatch, used for pre-auth lookups (resolving a user by email/phone before `orgId` is known during login) — explicitly documented as not for business logic.

**Guard enforcement**: `checkTenantGuard(model, operation)` is a no-op unless `config.tenantGuardMode !== 'off'`. If the model is in the 62-entry `ORG_SCOPED_MODELS` set and there is no ALS context at all (not even a bypass marker), it either logs a warning (`mode: warn`) or throws (`mode: enforce`). Critically: **any** context — including a `runSystemQuery` bypass — satisfies the guard; the guard's job is to catch code that forgot to enter *any* tenant frame, not to enforce per-row `orgId` filtering (that remains the query author's responsibility).

**Refresh rotation with reuse detection** (`refresh-token-service.ts`): tokens are opaque 32-byte base64url values, stored only as SHA-256 hashes. Each token belongs to a `familyId` chain. On rotation: a revoked-token-presented event is treated as theft (revokes the whole family, calls `auditSecurityCritical`); a used-token-replayed-within-grace-window event is treated as a benign multi-tab race (issues a new token inheriting the *original* expiry, not extending session lifetime); replay outside the grace window is theft; a naturally expired unused token is just `RefreshInvalidError`, not theft.

## 5. Technical Architecture

- `backend/src/shared/tenant/tenant-context.ts` — `AsyncLocalStorage` wrapper, `enterTenantContext`, `withTenant`, `runSystemQuery`, `requireTenantContext`, `runWithRlsApplied`.
- `backend/src/shared/tenant/tenant-guard.ts` + `org-scoped-models.ts` — the enforcement check and its allow-list.
- `backend/src/shared/database/prisma-client.ts` — 4 chained `$extends()` layers: null-byte stripping, phone normalization, tenant-guard, and an optional RLS `SET LOCAL` wrapper.
- `backend/src/modules/auth/{auth-middleware,auth-service,refresh-token-service,security-audit}.ts`.

## 6. API Specifications

Not a public API surface — this is cross-cutting middleware/infrastructure consumed by every other module's routes. The externally visible contract is: `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, and the `Authorization: Bearer <jwt>` header requirement on all protected routes (distinct from the public `X-Api-Key` surface, which resolves `orgId` through a separate, non-JWT path).

## 7. Database Schema

`User.jwtTokenVersion` (legacy revocation counter), `RefreshToken` (hashed token, `familyId`, expiry, revoked flag), `User.role` (legacy, dual-read alongside the RBAC `permissionGroupId` — see the RBAC spec). No schema changes proposed; this spec documents the existing shape.

## 8. Security Considerations

- **Staged enforcement, not yet fully at the database layer**: the design is explicitly phased — Phase 0 (context only) → Phase 1a (app-layer guard, `tenantGuardMode` gated) → Postgres Row-Level Security (the intended real boundary, a separate migration, gated by `config.rlsSetConfig` which is **off by default**). Today's actual enforcement is app-layer defense-in-depth; RLS is not yet the enforced barrier in the default configuration. This is worth flagging to the security team as a live gap between intended and current enforcement posture.
- **`runSystemQuery` is a deliberately unguarded escape hatch** — any new usage of it should be reviewed; it is documented as pre-auth-only.
- Refresh-token reuse detection is a real, tested mitigation (see `tests/security/refresh-token-service.test.ts`) against a stolen-token replay attack, not merely session expiry.

## 9. Performance Requirements

Not formally specified. The 15-minute-access-token design trades a DB roundtrip (removed per-request) for a bounded revocation-latency window — a deliberate performance/security trade-off documented in the code, not an oversight.

## 10. Testing Strategy

Covered by `backend/tests/security/`: `auth-flow.test.ts`, `refresh-token-service.test.ts`, `require-active-user.test.ts`, `security-audit.test.ts`, `tenant-context.test.ts`, `tenant-guard.test.ts` — this is one of the most thoroughly-tested subsystems in the codebase, consistent with `backend/CLAUDE.md`'s explicit rule that security-sensitive changes require a `tests/security/` test.

## 11. Deployment & Operations

Fail-fast boot check (`backend/src/config/index.ts`): `JWT_SECRET` must be set, non-default, and ≥32 characters in production, or the process refuses to start — "better to crash boot than run prod with forgeable secrets" per the code comment.

## 12. Timeline & Dependencies

Already shipped; refresh-token rotation was called out as a headline v3.4.0 feature (`CHANGELOG.md`: "access token ngắn + refresh token rotation").

## 13. Trade-offs & Rationale

- **Skipping per-request DB re-check for 15-minute tokens** trades a small revocation-latency window for removing a DB roundtrip from every authenticated request — a reasonable trade for this token lifetime, but would need revisiting if the access-token TTL were ever lengthened.
- **App-layer tenant guard before RLS** is a pragmatic incremental rollout (ship the cheaper layer first, add the DB-enforced layer once proven), but means the *current* production posture relies on every query author remembering to enter tenant context correctly — RLS would remove that human dependency entirely once enabled.
