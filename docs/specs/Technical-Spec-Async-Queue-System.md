# Technical Specification: Async Queue & Background Job System

> Generated by `nqdev-codebase-analyst` (Phase 4) on 2026-08-21. Companion to `docs/Queue-Flow-Diagrams.md` (Phase 4.5), which has the full flow diagrams and per-job schedule table — this spec covers the architectural design decisions behind that system rather than duplicating the inventory.

## 1. Overview

ZCRM runs two categories of background work: a small number of true message queues (BullMQ on Redis) for work that benefits from durability, retry, and controlled concurrency, and a larger set of `node-cron`/interval-based scheduled jobs for periodic sweeps that don't need queue semantics. Understanding *why* a given piece of work is a queue vs. a cron job is useful context this spec captures.

## 2. Problem Statement

Background work in a Zalo-integrated CRM ranges from "scan 500 group members, resumable if interrupted, must not run in parallel with itself" (queue-shaped: durable, resumable, rate-controlled) to "check every connected account's health every 5 minutes" (cron-shaped: periodic, stateless per run, naturally self-limiting). Using the wrong tool for either — cron for durable multi-step work, or a queue for simple periodic sweeps — adds either fragility or unnecessary infrastructure complexity.

## 3. Proposed Solution

Reserve BullMQ for genuinely job-shaped work: discrete, resumable, individually-retryable units of work triggered by a specific event (a user clicking "scan this group"), not by the clock. Everything clock-triggered uses `node-cron` or a jittered `setInterval`. In this Community checkout, exactly one queue (`group-scan`) meets that bar; a second (`zalo-label-mutate`) was built but deliberately deferred; everything else — 14 jobs — is cron/interval-based.

## 4. Detailed Design

**Why `group-scan` is a queue, not a cron job**: scanning a large Zalo group's membership is triggered by a user action (not the clock), takes long enough to need resumability (`resumeCursor`, 50-member chunks), benefits from BullMQ's built-in retry/backoff on transient Zalo API failures, and must be rate-limited to concurrency 1 to avoid Zalo's anti-spam detection — none of which `node-cron` provides natively.

**Why the cron jobs stay cron jobs**: friend sync, health checks, presence refresh, and the scoring/engagement sweeps are all periodic by nature (run every N minutes regardless of triggering events) and are individually idempotent/self-contained per run — they don't need persistence of in-progress state across a crash the way a multi-chunk group scan does. Using BullMQ's repeatable-job feature for these would add operational surface (queue monitoring, job-id management) without a corresponding benefit.

**Jitter as thundering-herd prevention**: `scoring-scheduler.ts`'s decay job deliberately avoids a fixed cron minute, using an hourly base plus up to 60 seconds of random jitter — explicitly to prevent every scoring computation from firing at exactly `:00` and creating a load spike, a pattern not used elsewhere in the codebase (most cron jobs use fixed schedules), suggesting scoring was identified as the one job whose load profile justified the extra complexity.

**Self-isolating Community queue connection**: the `group-scan` queue deliberately does *not* use the shared `redis-connection.ts` helper, instead building its own inline `ioredis` connection — an explicit anti-`_ee`-coupling design so Community's only queue has zero import surface toward the Enterprise bundle (enforced by a `check-no-ee-leak.sh` script). This is a stronger isolation guarantee than strictly necessary for one queue, but establishes the pattern any future Community queue should follow.

## 6. API Specifications

Not directly exposed — queue/cron triggering happens through domain routes (e.g. `POST /zalo-accounts/:id/group-scan`) or purely internally (crons have no HTTP surface at all).

## 7. Database Schema

`GroupScan`/`GroupMember` (queue-backed state), plus the various tables each cron job reads/writes (`ZaloAccount`, `ScoringConfig`-adjacent tables, `AppointmentReminder`-adjacent fields, `MediaAsset` for trash GC) — no schema changes proposed by this spec.

## 8. Security Considerations

None specific to the queue mechanism itself beyond what's already covered in `docs/Queue-Flow-Diagrams.md` (no DLQ, no alerting — operational gaps, not security ones). The self-isolating Redis connection pattern (§4) is a supply-chain/coupling hygiene measure, not a runtime security control.

## 9. Performance Requirements

Not formally specified for any job. The Redis instance backing BullMQ is sized (`maxmemory 256mb`) with a specific documented capacity assumption ("~35K jobs cumulative, 5K KH/day × 7 days") — any future queue addition should be checked against this budget rather than assumed to have headroom.

## 10. Testing Strategy

`group-scan-*.test.ts` covers the one live queue. No test exists for the deferred `zalo-label-mutate` queue's actual worker behavior (reasonable, since it's unwired) — if it's ever activated, it should gain equivalent coverage before going live, mirroring `group-scan`'s test pattern.

## 11. Deployment & Operations

Redis is a hard Compose dependency (no `profiles:` gate) — the system will not boot correctly without it, unlike ClamAV (optional, fail-open). This should be treated as a first-class production dependency in any deployment runbook, not an optional add-on.

## 12. Timeline & Dependencies

The BullMQ/Redis dependency was introduced as part of what in-code comments call "Luồng Mục Tiêu M1" (2026-06-01) — the `group-scan` queue and the Redis `profiles:` removal both date to that same change, suggesting BullMQ adoption and group-scan shipping were the same initiative.

## 13. Trade-offs & Rationale

- **One queue, many crons** is a proportionate design for the current feature set — introducing BullMQ for every periodic job would be over-engineering; reserving it for the one genuinely job-shaped workflow (group scan) keeps operational surface minimal.
- **No DLQ, retention-based audit trail instead** (see `docs/Queue-Flow-Diagrams.md` §1) trades automated failure handling for operational simplicity — acceptable at current scale/failure-rate, but worth revisiting if `group-scan` failure volume grows enough that manual 7-day-window inspection stops being practical.
- **Deferring `zalo-label-mutate` rather than deleting it** keeps a correct, ready-to-activate solution available for a race condition (`updateLabels` replacing the whole label structure) that may or may not currently be a live problem — a reasonable "solved but not yet needed" state, though it does mean dead code sits in the tree until someone makes that call.
