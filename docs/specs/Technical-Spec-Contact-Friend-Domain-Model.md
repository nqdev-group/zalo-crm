# Technical Specification: Contact/Friend Two-Book Domain Model

> Generated by `nqdev-codebase-analyst` (Phase 4) on 2026-08-21. Describes the shipped implementation as found in `backend/prisma/schema.prisma` (`Contact` at line 513, `Friend` at line 1882) and consuming code across `backend/src/modules/contacts/`, `frontend/src/composables/use-{contacts,friends}*.ts`.

## 1. Overview

ZCRM's foundational domain decision is splitting "a customer" into two related records: **Contact** (the person, as a manager sees them) and **Friend** (a specific Zalo-nick's relationship with that person, as a sales rep sees them). This spec documents why the split exists, how the two are kept consistent, and where the model's sharp edges are.

## 2. Problem Statement

A single customer may be in contact with a sales team through more than one Zalo nick — they friended one rep on nick A, later got connected to nick B through a group, and a third rep manages a related account. A naive single-table Contact model forces an impossible choice: either merge all nick-relationships into one row (losing per-rep working context and creating write contention/privacy leakage between reps who share visibility on "the same" contact), or keep contacts fully separate per nick (losing the manager's ability to see "this is one person" across the team).

## 3. Proposed Solution

Keep both views as separate, related tables. `Friend` is the unit of per-nick relationship truth — one row per `(zaloAccountId, zaloUidInNick)` pair — and is where day-to-day sales activity (scoring, message previews, tags, relationship status) actually happens. `Contact` is a derived, person-level aggregate — the manager/dashboard view — computed *from* its linked `Friend` rows, not an independently-maintained record.

## 4. Detailed Design

**Cardinality**: 1 `Contact` → N `Friend`, via `Friend.contactId`.

**Aggregation direction is Friend → Contact, not the reverse**: `Contact.leadScore` is explicitly a `MAX()` over the linked `Friend.leadScore` values — the *real* scoring computation happens per-Friend (4-axis: Engagement/Intent/Fit/Velocity), and Contact only ever displays the best/most-engaged relationship's score. Similarly, `Contact.acceptedNicksCount`/`pendingNicksCount`/`chattingNicksCount` are counters derived from the set of linked Friends' `friendshipStatus` values, and `Contact.priorityScore` is a documented formula (`leadScore×0.55 + engagementScore×0.30 + trendBoost`) that also ultimately traces back to Friend-level signal.

**Per-nick privacy isolation**: `Friend` carries its own last-inbound/outbound message previews, distinct per Friend row — by design, a sales rep with visibility on "this contact" through their own nick does not see another rep's nick's private message preview for the same underlying person. This is an explicit anti-leak design choice, not an accidental side effect of the schema shape.

**Visible parent filter**: managers/dashboards query `contacts WHERE merged_into IS NULL` — a Contact that's been merged into another (duplicate resolution) stops being independently visible, its history absorbed into the surviving parent.

**Two distinct grouping mechanisms, not one**: `mergedInto` is a *hard* merge (duplicate resolution — the merged Contact effectively stops existing as a separate entity going forward). `parentContactId` is a *soft* link for cross-Zalo-identity human-level grouping (the same person, deliberately still tracked as related-but-distinct Contacts) — these solve different problems and should not be conflated when reasoning about the schema.

**`relationshipKind` legacy value**: `Friend.relationshipKind` has valid values `friend | pending_friend | chatting_stranger | ghost`, but a `none` value exists in historical data as documented junk — the frontend explicitly coerces `none` to `chatting_stranger` for display (renders it the same blue color) rather than the backend cleaning up the legacy data. This is a known, accepted data-quality wart, not a bug to silently "fix" without understanding why it was left this way.

**Collaborator sharing**: `ContactAccess` is a separate junction table layering primary/collaborator visibility on top of the Contact/Friend structure — multiple users can be granted access to the same Contact independent of which Friend/nick relationship they work through.

## 8. Security Considerations

The per-Friend message-preview isolation (§4) is itself a privacy control — it prevents a visibility grant on "the Contact" from implicitly exposing another rep's private nick-level conversation content. Any future feature that flattens Friend data into a Contact-level view should preserve this isolation deliberately, not accidentally erode it.

## 13. Trade-offs & Rationale

- **Two tables instead of one** costs query complexity (most "show me this customer" UI needs both a Contact fetch and its Friend rows) but buys per-rep privacy isolation and multi-nick correctness that a single-table design cannot express cleanly.
- **Derived aggregates on Contact** (rather than Contact being independently editable) means Contact-level fields like `leadScore` are only as fresh as the last aggregation pass — a design that trades some potential staleness for a single source of truth (Friend) and avoids dual-write drift between "the Contact's own score" and "the sum of its Friends' scores."
- **Leaving the `relationshipKind: none` legacy value uncleaned**, coercing it at the frontend instead, avoids a backfill migration risk in exchange for permanent display-layer special-casing — a defensible short-term call that should eventually be revisited with an actual data cleanup if the legacy rows are still present.
