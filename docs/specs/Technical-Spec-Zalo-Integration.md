# Technical Specification: Zalo Account Pool & Integration

> Generated by `nqdev-codebase-analyst` (Phase 4) on 2026-08-21. Describes the shipped implementation as found in `backend/src/modules/zalo/` (largest module by file count, ~35 files).

## 1. Overview

ZCRM's core value proposition — CRM structure over existing Zalo conversations — depends entirely on maintaining live, stable connections to each org's Zalo accounts via the unofficial `zca-js` client. This subsystem manages connection lifecycle, session persistence, per-account rate limiting, and anti-block heuristics for potentially dozens of concurrently-connected Zalo "nicks" per organization.

## 2. Problem Statement

`zca-js` is an unofficial client wrapping Zalo's undocumented internal protocol — there is no official SDK, no guaranteed stability, and using it risks account suspension if usage patterns look automated. The system must: (a) keep many accounts connected reliably across server restarts, (b) avoid triggering Zalo's anti-spam detection through careful pacing, and (c) survive the inherent flakiness of an unofficial, reverse-engineered client without cascading failures.

## 3. Proposed Solution

A singleton `ZaloAccountPool` (`zalo-pool.ts`, 1,125 lines) holds an in-memory map of live SDK sessions, each tagged with an incrementing "epoch" to distinguish a current connection attempt from a stale one whose async callbacks fire late. Rate limiting is per-`(accountId, category)`, Redis-backed with an in-memory fallback, and fails open by design (a rate-limiter error never blocks a legitimate action — it only ever adds friction, never becomes a hard outage). All scheduled Zalo-facing work (friend sync, health checks, group scans) is deliberately sequential and staggered rather than parallel.

## 4. Detailed Design

**Session lifecycle**: `loginQR(accountId, proxyUrl?)` establishes a new SDK session via QR scan; `reconnect(accountId, credentials, proxyUrl?)` restores a session from persisted `sessionData`; `disconnect(accountId)` tears one down and — critically — sets `ZaloAccount.disconnectReason = 'manual'`, which is checked by every subsequent auto-reconnect sweep (health-check cron, daily refresh) to ensure a deliberate disconnect is never silently reversed ("ngắt là ngắt thật" / "disconnect means disconnect," per the code's own phrasing).

**Epoch-based flap prevention**: each connect/reconnect increments a per-account epoch counter. If a stale listener's `'closed'` event fires after a newer connection attempt has already superseded it, the event is ignored because its captured epoch no longer matches the pool's current epoch for that account — this specifically prevents a self-collision reconnect loop where an old, dying connection's cleanup logic fights a new, healthy one.

**Rate limiting** (`zalo-rate-limiter.ts`): per-`(accountId, category)` daily counter + burst window, Redis-backed when available, falling back to an in-memory `Map` — and the `checkLimits` call **catches all internal errors and returns `{allowed: true}`**, i.e. fail-open: a Redis outage degrades rate-limiting silently rather than blocking legitimate Zalo operations. Limits are not hardcoded constants — `getEffectiveLimit()` resolves nick-level override → org-level default → hardcoded fallback, cached 60 seconds, sourced from an editable `SdkLimit` DB table exposed in the "Quản lý nick Zalo" settings UI.

**Anti-block cadence** (all explicitly tuned, per code comments, against Zalo's undocumented anti-spam heuristics): friend full-sync runs every 15 minutes, sequential per account with a 200ms stagger; health-check reconnects run every 5 minutes, staggered 5-10s per account; the group-scan BullMQ worker runs at concurrency 1 system-wide; a 5-minute polling backup for group messages is capped to 20 groups / 50 messages per sync cycle.

**Cross-tenant event isolation**: account status events are emitted scoped to `org:<orgId>` Socket.IO rooms (`emitAccountEventToOrg`) rather than a bare `io.emit()` — the code comments explicitly reference this as a fix for a prior cross-tenant broadcast bug where account status (`{accountId, zaloUid}`) leaked across organizations.

## 5. Technical Architecture

- `zalo-pool.ts` — the singleton pool, `zca-js` loaded via `createRequire` CJS interop (no reliable ESM named exports from the SDK).
- `zalo-listener-factory.ts` (46.4K) — attaches all zca-js SDK event listeners for one account (group messages, undo, reactions, friend events).
- `zalo-rate-limiter.ts`, `sdk-limit-service.ts` — rate limiting and its editable-limits backing store.
- `zalo-message-sync.ts` — polling backup behind the primary event-driven message path.
- `friend-sync-cron.ts`, `zalo-health-check.ts`, `group-info-sync-cron.ts`, `status-log-checkpoint-cron.ts`, `presence-service.ts` — the ~7 scheduled jobs specific to this module.
- `group-scan-queue.ts` / `group-scan-worker.ts` — the one live BullMQ queue (see `docs/Queue-Flow-Diagrams.md`).
- `proxy-util.ts` — per-account HTTP/SOCKS5 proxy support.

## 6. API Specifications

Internal routes under `/api/v1/zalo-accounts/*` (connect, disconnect, reconnect, proxy config, group scan trigger) — not part of the public `X-Api-Key` surface except where explicitly documented in `docs/zalocrm-api/`.

## 7. Database Schema

`ZaloAccount` (session data, `privacyMode`, `disconnectReason`, per-nick daily caps), `SdkLimit` (editable rate-limit overrides), `ZaloAccountStatusLog` (uptime tracking, reconciled by the checkpoint cron), `GroupScan`/`GroupMember` (scan state and results).

## 8. Security Considerations

- Session data (`ZaloAccount.sessionData`) is sensitive — it's effectively a cookie/session credential for the underlying Zalo account. (Whether it's encrypted at rest was not directly confirmed in this pass — worth an explicit follow-up check against `prisma/CLAUDE.md`'s credential-column rule.)
- Fail-open rate limiting is a deliberate availability-over-strictness choice; it means a Redis outage cannot become a Zalo-operations outage, at the cost of the rate limit itself being unenforced during that window.
- Proxy configuration is per-account and admin-controlled — not currently documented as SSRF-guarded the way outgoing webhooks are (webhooks use `ssrf-guard.ts`); this is a different threat model (outbound Zalo SDK traffic, not admin-supplied arbitrary URLs), so the omission is likely intentional rather than an oversight, but worth confirming.

## 9. Performance Requirements

No formal SLA exists; the architecture is explicitly optimized for *not* triggering Zalo's anti-spam detection over raw throughput, and accepts a single-process, in-memory-session design (no horizontal scaling path today).

## 10. Testing Strategy

`zalo-profile-capture.test.ts` (the one module-colocated test in the whole backend), plus centralized tests: `group-scan-*.test.ts`, `friend-sync-*.test.ts`, `deleted-nick-*.test.ts`, `ghost-*.test.ts` — the ghost/deleted-nick tests specifically cover the flap-prevention and cleanup edge cases described in §4.

## 11. Deployment & Operations

Requires `REDIS_URL` (BullMQ + rate limiting), reconnects all persisted-session accounts at boot (filtered to real, non-archived UIDs — a documented anti-"ghost nick" guard), and gracefully stops the group-scan worker on `SIGTERM`/`SIGINT` before Fastify itself closes.

## 12. Timeline & Dependencies

Foundational since v1.0 ("Quản lý nhiều Zalo — Đăng nhập QR, tự kết nối lại"); proxy-per-account added v2.0; per-nick daily caps and `SdkLimit` editability are more recent additions supporting the v3.4 "Nâng cao bảo mật" line.

## 13. Trade-offs & Rationale

- **Fail-open rate limiting** trades strict enforcement for availability — a defensible choice given the rate limiter's purpose is self-protective (avoid Zalo bans), not a hard business rule; a false negative here costs less than a false positive (blocking legitimate sends).
- **In-memory pool, no horizontal scaling** is a real architectural constraint, not an oversight — Zalo sessions are inherently stateful per-process, and a multi-instance design would require session affinity or a shared-session redesign that doesn't currently exist.
- **Concurrency-1 group scan is a global, not per-org, limit** — simple to reason about, but a potential fairness/throughput issue in a busy multi-org deployment (see `docs/Queue-Flow-Diagrams.md` §Scaling Recommendations).
